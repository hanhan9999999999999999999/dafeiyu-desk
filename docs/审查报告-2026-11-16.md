## 二、缺陷清单

### P0-1 本地 HTTP 服务无来源校验（已修复）

**现象**：服务只绑 `127.0.0.1`，但对请求的 `Host` / `Origin` / `Sec-Fetch-Site` 一律不看，任何一路来源都直接进业务路由。

**证据（实测，非推断）**：`_app/_tmp/probe-csrf.js` 用真实 `startServer` 起在 7801 端口，四项全部命中：

| 探针 | 请求 | 修复前结果 |
| --- | --- | --- |
| 1 | `GET /` + `Origin: https://evil.example` | 200，正常返回应用页面 |
| 2 | `POST /usage/clear` + 恶意 Origin + `content-type: text/plain` | **200 `{"ok":true}`，服务端清空计数真实 +1** |
| 3 | `GET /api/packs/check?path=C:\Windows\win.ini` + `Host: evil.example:7801` | 200，适配器收到 `C:\Windows\win.ini` |
| 4 | `GET /usage/summary` 跨站 | 无 `access-control-allow-origin`，普通跨站读被浏览器挡 |

**影响链**：
1. `text/plain` 属于 CORS「简单请求」，浏览器不发预检 → 用户只要在挂件运行时打开任意网页，页面就能改状态。可打到 `/api/packs/<id>/remove`（`force` 强删模型包）、`/api/packs/import`、`/api/packs/active`（切模型）、`/usage/clear`、`/engine/tts`。
2. `Host` 不校验 = DNS rebinding 面：`evil.com` 重绑定到 `127.0.0.1` 后即为同源，探针 4 的「读不回来」立刻失效。
3. `/api/packs/check` 是任意本机路径存在性探针；配合 `/api/packs/import`（接受任意本机路径）+ `/packs/<id>/<rel>`（MIME 白名单含 `.json` `.txt` `.md`），可构成「导入目录 → 通过 HTTP 读回文本」的本地文件外带链路。

**修复**：`src/server.js:70` 新增 `sameOriginOk(req, port)`，在解析 URL 之后、所有业务路由之前统一准入（`src/server.js:113`）。判据三条：`Host` 必须是回环名且端口一致；`Origin` 存在时必须等于本站三写法之一；`Sec-Fetch-Site: cross-site` 直接拒。不通过返回 403 且只记一行日志（避免被刷爆 `run.log`）。
**说明**：`Origin: null` 也拒 —— 沙箱 iframe 与 `data:` 页都能伪造该值；应用页面全部由 `http://127.0.0.1:PORT` 加载，不依赖 `null` 源。

**验证**：`_app/_tmp/probe-guard.js` 10 项断言全过 —— 同源 GET/POST 正常（清空计数 0→1），跨站 POST / 伪造 Host / `Origin: null` / `cross-site` 全部 403 且状态未被改动，无 Origin 的本机脚本（npm 测试路径）不受影响。

### P1-1 RVC 错误分支引用作用域外变量（已修复）

**现象**：`/engine/rvc` 上游返回非 2xx 时，客户端拿到 `500 {"ok":false,"error":"e is not defined"}`。

**根因**：原 `src/server.js:470` 在 `if (!r.ok)` 分支里写 `Number(e && e.statusCode) || 500`，而该分支内没有 `e`（真正的 `catch (e)` 在其后）。求值即抛 `ReferenceError`，被外层 catch 接住，上游的真实状态码与错误文本全部丢失 —— 用户看到的是一条毫无信息量的内部错误。

**修复**：改为 `const code = Number(r.status)`（`src/server.js:510`），仅接受 400–599，其余回 500。
**验证**：`_app/_tmp/probe-rvc-err.js` 三项断言全过：状态码 `400` 与上游一致、错误文本 `模型文件损坏（no such model）` 完整透传、响应中不再出现 `e is not defined`。

### P1-2 五处 `spawn()` 未挂 `error` 监听（已修复）

**现象**：子进程启动失败（ENOENT / EACCES / 安全软件拦截）时没有 `'error'` 处理器。

**影响**：`child_process` 的启动错误是异步事件，无人接住就落到 `process.on("uncaughtException")`，被 `recordCrash` 静默吞掉；而状态机已经把进程标记为「已启动」，用户侧表现为「显示运行中但永远没有声音/回复」，且崩溃记录里只有一条与用户操作无关的异常。

**修复位置**：`src/main.js:200`（RVC）、`:630`（自带桥接）、`:745`（RVC 环境安装）、`:824`（XTTS 安装）、`:914`（飞鱼安装）。四处安装进程的错误还会 `push()` 到设置页日志，用户能直接看到「安装进程起不来：…」。
**加固点**：`rvcPython()`（`src/main.js:145`）已先 `existsSync` 再 spawn，ENOENT 概率低，但 EACCES 与安全软件拦截无法预判，本次补丁覆盖了这条路径。

### P1-3 `diag:open` 接受任意路径（已修复）

**现象**：`preload.js:243` 暴露 `diagOpen(p)` → `ipcMain.handle("diag:open")` → `shell.openPath(String(p || ""))`，主进程不校验路径。`shell.openPath` 对 `.exe` / `.bat` 是**执行**而非仅打开。

**现状评估**：实际调用方只有 `settings-renderer.js:2798`（传主进程给出的 `lastDiagDir`），故当前不可直接利用；但这是一条「渲染层 → 主进程任意路径打开/执行」的通道，任何一处未来 XSS 都能接成提权跳板，属必须收紧的设计。

**修复**：`src/main.js:5097` 起把路径 `path.resolve` 后与 `app.getPath("userData")` 求相对路径，越界（`..` 或绝对路径）直接拒绝并回 `只允许打开诊断目录`。

### P1-4 密钥明文落盘（已修复）

**证据**：`src/settings.js:75` `apiKey: ""` 与 `seeKey` 同属 `settings.json` 字段；`src/main.js:4161` 的 `SECRET` 集合只在**导出诊断包**时脱敏，落盘本身是明文 JSON。渲染层 `settings-renderer.js:1824` 直接回填明文。

**影响**：`%APPDATA%\dafeiyu-desk\settings.json` 被任何本机进程 / 备份 / 同步盘 / 误发诊断包读取即泄露模型 API Key，可被盗刷。

**已实施**：
1. `src/settings.js`：新增 `SECRET_KEYS = ["apiKey","seeKey"]` 与 `SAFE_PREFIX = "safe1:"`；`Settings(dir, crypto)` 可注入加密器；`security` 密文写在文件顶层 `secure: {}` 区，**不进 `sanitize()` 的字段规则**（`seeKey` 那条 400 字符截断会毁掉密文，这是刻意绕开的）；`attachCrypto()` 负责「挂上加密器 → 重载 → 一次性把明文迁成密文」；`secureState` 四态 `encrypted / plaintext / locked / error`。
2. `locked` / `error` 时**密文一律保留**（`_keepBlob` 回写），只用空值表示「这次读不到」—— 否则一次密钥库故障就把用户 key 永久抹掉。
3. `src/main.js`：`attachSecretStorage()` 接 `safeStorage`（Windows 下是 DPAPI 包住的主密钥 + AES-GCM，密文带 `v10` 头）；不可用时 `logErr` 明说「仍以明文保存」，不假装安全。
4. 渲染层掩码：`settings:get` 与发给设置窗口的 `settings-changed` 里，密钥替换为 `sk-••••4f2a`；输入框显示掩码，**没改动就不提交**；`settings:patch` 另有一道「值含 `••` 直接丢弃」的防线。「测试连接」未改 key 时不带 key 上传，由主进程用存着的那份。

**验证**：
- `scripts/test-secrets.js`（新增，挂在 `npm test` 与 `npm run verify` 上）：11 条断言全过 —— 明文迁移、盘上无明文、新实例解回、locked 不销毁密文、error 有原因且不覆盖、patch 其它字段不冲掉密钥、清空即删、1200 字符长 key 完整往返、已加密文件不重写、`secure` 区拒收未知键、坏 JSON 仍备份回默认。
- 真机探针 `_tmp/probe-safestorage.js`（经 `smoke-electron.js --main-eval-file` 在 Electron 35.7.5 主进程里跑，15 项全过）：`isEncryptionAvailable=true`、往返一致、密文被改一字节即抛错、落盘无明文、`locked` 后密文仍在、恢复加密器后 key 读得回。
- 全量 `npm run verify`：**exit 0**（verify-src 1058/0、verify-packs 24/0、verify-pack 43/0、verify-server 14/0、20 个单元套件全绿、audit-settings 70 键/52 文件、test-persist 31/0、audit-network 8/0、audit-privacy 13/0、audit-listeners 7/0）。

**边界（写在明处）**：DPAPI 只保护**静态文件** —— 同一 Windows 账户下运行的恶意进程仍可解密；主窗口渲染进程里仍持有明文（`src/voice.js` 在渲染层直连 API，本次未改架构）。这两条不再当作缺陷，但也不谎称已被挡住。

### P1-5 安装包未签名（已修配置 · 待证书）

**证据**：`package.json` build.win 段原为 `signAndEditExecutable: false`、`forceCodeSigning: false`，且无 `certificateFile` / `signtoolOptions`。

**影响**：
1. 用户下载后 SmartScreen 报「未知发布者」，转化率与信任度直接受损；
2. 企业环境（AppLocker / WDAC / 组策略）通常直接拦截未签名 exe；
3. 无法验证来源，与 P2-1 的供应链风险叠加。

**已实施**：
1. `build.win.signAndEditExecutable: true`（rcedit 写版本/图标资源，并让签名链路生效）、`signingHashAlgorithms: ["sha256"]`；`forceCodeSigning` 保持 `false`，避免无证书的机器出不了包。
2. 新增 `scripts/sign-check.js` + `npm run sign:check`：读 `Get-AuthenticodeSignature`（Status / 主体 / 有效期 / 指纹）与 `VersionInfo`，输出人话结论；`--strict` 时未签名即 `exit 1` —— 作为发布门的硬判据，而不是靠 SmartScreen 弹窗发现问题。
3. 新增 `docs/发行-签名与密钥.md`：OV/EV/Azure Trusted Signing 选型、`CSC_LINK`/`CSC_KEY_PASSWORD` 与证书存储两条接线方式、时间戳、SmartScreen 信誉现实预期、验收命令。
4. 实测当前产物：`FileVersion 1.3.2` / `CompanyName 小代码酱` / `ProductName 大肥鱼` 齐全，`数字签名：⚠ 未签名（Status=2）` —— 与「本机没有证书」一致。

**还剩什么**：证书本身（硬件令牌或云签名服务），以及带证书跑一次 `npm run build` → `npm run sign:check -- --strict`。这一步无法在无证书的机器上完成，也不能伪造。

### P2-2 设置落盘的两个小隐患（未修复 · 建议项）

1. `src/settings.js` 的 `save()` 用 `writeFileSync(tmp)` + `renameSync` 原子落盘，但 **tmp 文件名固定**（`.tmp`）。两个窗口同时 patch 会互踩同一个临时文件，极端情况下 rename 到一半内容错乱。建议 tmp 名带 `process.pid` + 随机后缀。
2. `patch()` 每次都同步读盘再 merge（这是防多窗口互相覆盖的正确设计），但若渲染层滑块 `input` 事件未节流，会变成高频同步 IO。建议在渲染层对连续型控件做 100–150ms 防抖，或在主进程合并 16ms 内的多次 patch。

### P2-3 `/api/packs/import` 接受任意本机路径（部分缓解）

`src/packs/http.js` 的 import 分支直接取 `b.path`，`.zip` 走 `importArchive`，否则 `importDir`。P0-1 修复后已挡住跨站调用，但仍建议：import 只接受「用户通过系统文件对话框选出的路径」（主进程登记一次性令牌），或至少对目标目录做一次「是否含 `.model3.json`」的前置校验再复制，避免误把整个 `Documents` 拷进模型库。

### P2-4 Crashpad 目录无清理策略

`src/main.js:5536` 只注册了 `userData/Crashpad/reports` 路径，未见容量/条数上限。长期使用会累积 dump 文件（每个数十 MB）。建议启动时按条数与总量双阈值裁剪（保留最近 20 个 / 200 MB）。

### P2-5 仓库卫生

`_app/_tmp/` 留有历史临时脚本与探针（其中 `patch-r19.js` 存在编码损坏、`node --check` 直接失败；另有 `install-report.json`、若干 `audit-*.js`）。这些不进打包（`files` 只收 `src/**`），但会干扰后续静态扫描与新人判断。建议移入 `_archive/` 或加 `.gitignore`。

### P3 级观察（不阻塞发行）

- 渲染层多数 `on*` 订阅不返回退订函数（`onModelImportProgress` / `onIdleProgress` / `onWindowShown` / `onGameMode` 除外）。页面重载即随 context 销毁，可接受，但与「订阅在 finally 退订」的既有规范不完全一致。
- 无类型系统、无 ESLint/Prettier 门禁，风格靠人工约定维持（现有代码风格确实统一，风险在未来）。
- 界面文案硬编码中文，无 i18n 抽取层。
- `src/main.js` 5,985 行、`renderer.js` 3,260 行，单文件职责偏多；商业化迭代前建议按「窗口管理 / 引擎控制 / IPC 聚合」拆三层。
