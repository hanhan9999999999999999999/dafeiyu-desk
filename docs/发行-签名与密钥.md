## 一、代码签名（P1-5）

### 1.1 现在的配置

`_app/package.json`：

```json
"win": {
  "signAndEditExecutable": true,
  "forceCodeSigning": false,
  "signingHashAlgorithms": ["sha256"]
}
```

| 字段 | 作用 | 为什么这么设 |
| --- | --- | --- |
| `signAndEditExecutable: true` | 让 electron-builder 调 rcedit 把版本号、图标、产品名写进 exe 资源；有证书时顺带签名 | 原来是 `false`，exe 的版本资源只能靠 Electron 自带的默认值，安装包属性里看不到厂家信息 |
| `forceCodeSigning: false` | 没有证书时仍然出包（只告警，不失败） | 开发机/CI 没有证书也要能打测试包。**发布机上会带证书，届时产物自然被签** |
| `signingHashAlgorithms: ["sha256"]` | 签名摘要算法 | 老签名工具默认 SHA-1，Windows 10 1903 之后不再接受 SHA-1 签名 |

`forceCodeSigning` 建议**长期保持 false**，而把「必须签名」这件事交给发行门：

```powershell
npm.cmd run sign:check -- --strict
```

`--strict` 下产物没有有效签名就 `exit 1`，CI 里这一步挂了就不许发。这样开发机不受影响，发布链路不缺门。

### 1.2 证书怎么选

| 类型 | 说明 | 现状适配 |
| --- | --- | --- |
| **OV**（Organization Validation） | 需要企业营业执照 + 电话回拨，签发 1–3 天；私钥在 U 盘/HSM 或云签名服务 | 性价比路线，常规桌面软件够用 |
| **EV**（Extended Validation） | 审核更严，硬件令牌；**签出来的包对 SmartScreen 立刻有信誉** | 想在第一天就不弹「Windows 已保护你的电脑」就得它 |
| **Azure Trusted Signing** | 微软自家云签名，按月计费，不用管证书过期 | 如果构建跑在 Azure/GitHub Actions，这条最省事 |

⚠ 2023 年 6 月之后，CA/B Forum 要求代码签名私钥必须存放在硬件或云 HSM 里，**拿不到可以直接拷来拷去的 .pfx 了**（新签发的都是硬件令牌或云服务）。所以下面两条路线只能选一条：
- 有硬件令牌 → 在**带令牌的发布机**上本地构建
- 用云签名（Azure Trusted Signing / SSL.com eSigner 等）→ CI 里配凭据

### 1.3 配好之后怎么让 electron-builder 用上

**路线 A：本机 .pfx（老证书仍在有效期内时可用）**

```powershell
$env:CSC_LINK = "D:\certs\dafeiyu.pfx"        # 也可以是 base64 字符串
$env:CSC_KEY_PASSWORD = "证书密码"
npm.cmd run build
npm.cmd run sign:check -- --strict
```

**路线 B：证书装在 Windows 证书存储里**

```json
"win": {
  "certificateSubjectName": "小代码酱",
  "certificateSha1": "……"
}
```

**路线 C：Azure Trusted Signing**

```json
"win": {
  "azureSignOptions": {
    "publisherName": "……",
    "endpoint": "https://xxx.codesigning.azure.net",
    "codeSigningAccountName": "……",
    "certificateProfileName": "……"
  }
}
```

> 无论走哪条，**时间戳别关**。electron-builder 默认用 `http://timestamp.digicert.com`，签名不带时间戳的话，证书一过期，之前发出去的包全部变成「签名无效」。

### 1.4 验收

```powershell
cd "D:\document\DSH Live2D\_app"
npm.cmd run build                  # 出包（dist\win-unpacked\大肥鱼.exe + 安装包）
npm.cmd run sign:check             # 看状态：版本资源 / 签名主体 / 有效期
npm.cmd run sign:check -- --strict # 发行门：没签名就 exit 1
```

`sign-check.js` 会打印：

```
版本资源：
  FileVersion       1.3.2
  CompanyName       小代码酱
  ...
数字签名：
  ✅ 已签名 · 证书主体：CN=……
     有效期至 2027-11-16 08:00:00
exe 资源写入：✅ 有版本信息（signAndEditExecutable 生效）
```

**当前状态（2026-11-16 实测）**：`dist\win-unpacked\大肥鱼.exe` 192 MB，版本资源齐全（小代码酱 / 大肥鱼 / 大肥鱼 · 桌面 Live2D 伴侣），`数字签名：⚠ 未签名或签名无效（Status=2）`。这是因为本机没有证书 —— 配置位置已经就绪，缺的只有证书本身。

### 1.5 SmartScreen 的现实预期

- **OV 证书**：即使签了名，新证书也没有信誉积累，前期仍会弹一次「Windows 已保护你的电脑」，需要用户点「更多信息 → 仍要运行」；下载量上去之后才慢慢转好。
- **EV 证书**：签名即信誉，第一天就不弹。
- 用户点过「仍要运行」之后，该文件的哈希会在本机留下记录，后续同版本不再弹。

## 二、密钥存储（P1-4）

### 2.1 存的是哪两个

`apiKey`（对话模型）与 `seeKey`（看屏幕的外部视觉接口）。两者都在 `settings.json` 里，原来都是明文。

### 2.2 加密方式

用 Electron 的 `safeStorage`（Windows 下就是 DPAPI）：

```js
encrypt: (plain) => "safe1:" + safeStorage.encryptString(plain).toString("base64")
```

- 密文绑定**当前 Windows 用户账户**。同一台机器换个账户、或者把 `settings.json` 拷到别的机器，都解不开 —— 这是设计意图，不是 bug。
- `settings.json` 里的形态：

```json
{
  "scale": 1,
  "apiBase": "https://api.deepseek.com",
  "secure": {
    "apiKey": "safe1:AQAAANCMnd8BFdERjHoAwE/Cl+sBAAAA…"
  }
}
```

顶层**不再有** `apiKey` / `seeKey` 字段。`secure` 区只认 `SECRET_KEYS` 里的两个名字，塞别的键（比如想借它改 `volume`）会被忽略。

### 2.3 四个状态

`Settings.secureState`，会在启动日志里打一行 `[main] 密钥存储：encrypted`：

| 状态 | 含义 | 用户看到什么 |
| --- | --- | --- |
| `encrypted` | 正常：盘上是密文，内存里是明文 | 设置页输入框显示掩码 |
| `plaintext` | 系统密钥库不可用（极少数精简系统 / 策略禁用 DPAPI），退回明文 | 设置页顶部提示「系统密钥库不可用，密钥以明文保存」 |
| `locked` | 盘上有密文，但这次启动没拿到加密器；**密文保留不删** | 输入框空白；重新配置或恢复密钥库后能自动读回 |
| `error` | 有加密器但解不开（换过账户 / 密钥库被重置）；**密文保留** | 提示「密钥解不开……请在设置里重新填写」 |

`locked` / `error` 两种状态下，`save()` **不会**用空值覆盖掉盘上的密文 —— 一旦覆盖，原密钥就永久没了。这一点由 `scripts/test-secrets.js` 的 ④⑤ 两条断言守着。

### 2.4 老版本升级

老版本 `settings.json` 里是明文。新版本第一次启动时：

1. `load()` 读到明文 `apiKey`；
2. 发现系统密钥库可用 → 标 `needsEncrypt`；
3. `save()` 立刻重写成密文，明文从盘上消失。

**只在需要时写一次**：已经是密文的文件再启动不会重写（内容和 mtime 都不变），避免每次开机都碰盘。

### 2.5 设置页的掩码

设置页拿不到明文：

- `settings:get` 与 `settings-changed`（发给设置窗口的那份）里，密钥是掩码：`sk-••••4f2a`；短于 9 个字符时统一显示 `••••••`。
- 输入框里就是这串掩码。**用户不碰它，就不提交**（渲染层比对 `el.value === el.dataset.mask`）；一改动就提交真实值；清空即删除该密钥。
- 主进程侧还有一道防线：`settings:patch` 收到含 `••` 的值直接丢弃，防止旧页面或手写调用把掩码存成密钥。
- 「测试连接」按钮：用户没改密钥时**不带 key** 上传，主进程用存着的那份（`cfg.apiKey === undefined` 走 `S.get("apiKey")`）；传空串才是「用户清空了」。

主窗口仍然拿明文 —— `src/voice.js` 在渲染进程里直接请求 API，拿不到 key 就说不了话。这是架构现状，不是本次遗漏。

### 2.6 边界说清楚

| 威胁 | 是否被这次改动挡住 |
| --- | --- |
| 别的程序读 `%APPDATA%\dafeiyu-desk\settings.json` | ✅ 只有密文，且只有当前用户能解 |
| 备份/同步盘把 settings.json 带到别的机器 | ✅ 解不开（附带的提示会让用户重填） |
| 本机另一个 Windows 用户读该文件 | ⚠ 取决于文件 ACL（`%APPDATA%` 默认只给本用户），DPAPI 那层他也解不开 |
| 同一个用户下运行的恶意程序 | ❌ 它能调同一个 DPAPI 解密。静态加密挡不住同账户的活体恶意代码 |
| 主窗口渲染进程内存里的明文 | ❌ 见 2.5 末段 |

改动前的原件在 `D:\备份\20261116-161644-密钥与签名\`（`main.js` / `settings.js` / `settings-renderer.js` / `package.json`，SHA256 已核对）。
