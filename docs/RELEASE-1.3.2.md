# 大肥鱼 1.3.2

2026-11-16 · Windows 10 / 11 x64 · 930,561,403 B（约 887.5 MB）

从 1.3.1 到这一版，改动集中在三件事：**开口快了多少**、**出错时她说人话**、**她花的钱看得见**。
下面按「你会感知到的变化」写，不按提交顺序。

## 语音：首声更快，而且第一句不会被下一句掐断

飞鱼（本机 CosyVoice）这条链路被逐段量过、逐段修过：

- **首声**：6 / 27 / 72 字三条代表性文本，冷启动三次取中位 —— 首块到达 **2.58 / 2.03 / 3.05 秒 → 1.79 / 2.08 / 1.94 秒**，
  整段合成耗时下降 10%–21%。做法不是砍模型，而是把四处在白等：
  1. 每句都重新扫一遍参考音频目录、把 manifest 读三遍 → 改成按 mtime 缓存的元数据（`/health` 往返 6.8–9.7ms → 2.1ms）；
  2. 每句都重抽参考音色的说话人特征（0.3–0.8 秒）→ 开机预热时把七条参考音的特征一次全抽，请求里省掉；
  3. 上一句把 `token_hop_len` 推到 100 就不复位，下一句首块要等 100 个 token 才吐 → 每句进锁先拨回 25；
  4. 换参考音会重新跑一次「预热推理」（1.6–2.2 秒）放在用户等的第一句上 → 从请求路径彻底撤掉。
  另外两件**不能做**的事也钉进了注释：`cudnn.benchmark=True` 会让流式分块每换一个长度就穷举卷积算法（27 字那句 RTF 1.21 → 14.25）；把 CosyVoice 的轮询从 100ms 压到 20ms 反而更慢（GIL 争用）。
- **同一句话音色不再跳**：参考音按情绪挑，但一句一请求，段内会换人 → 同一轮回复锁同一条参考音（25 秒窗口）。
- **第一句被掐断**（1.3.1 就存在、这一版修掉）：`createPcmPlayer().end()` 原来只看「已经排进时间轴的块」，
  而块还卡在 `decodeAudioData` 里，于是立刻判定「播完了」，第二句开播把第一句盖掉。现在先等解码链落地再看时间轴；
  `drain()` 起手也先等第一句播完。**只有第一句走这条路，所以只有第一句有这个问题。**
- **句间空档**：以前每句 `new Audio(url)`，句间靠 media 元素自己加载；现在剩余句子全 `fetch` 下来推进同一根
  WebAudio 时间轴，采样级首尾相接。上下文被系统挂起时还会先 `resume()`，避免第一块被排到「过去的时刻」。
- **量过的证据**：离屏用真 `AudioContext` 排三条 WAV（0.8/1.2/1.0 秒，120ms 间隔陆续到达）
  → 3.0 秒音频 3.12 秒播完、`end()` 等足 2.74 秒，判定 GApLESS-OK；真机日志里
  「首句播完 8.76s（音频 6.28s）」——只会比音频长，不会提前收工。

## 出错的时候说人话

- **断线**：以前攒够两次失败就甩一句「我这边连不上 DSH 了」。现在先自愈一次，能救就改口说
  「原来那个地址（8899）没应答，我改走随身桥接了。」；真没救才说「原来那个地址不通，随身桥接也没起来……」。
  报过断之后每三拍再自愈一次，通了自动回到「好了」。
- **发送时连不上**：不再丢句 —— 换到可用地址后把这句重发一遍。
- **一键自检不再说谎**：分开记「这个地址有没有桥答话」和「答话的是不是自带桥」，输入框也会真的改成新地址。
- **设置页一句话说清桥接状态**：外部桥在跑、自带桥在跑、地址被指过去了，各是各的文案。

## 桥接与引擎：卡死会自愈，外面起的也不再显示「未启动」

- 自带桥接拉起后**等端口真的应答**才宣告就绪（以前 spawn 完立刻写「已启动」，日志里永远跟着一句「还没答话」）；
  进程在但不应答 → 收掉重起；巡检从 90 秒收紧到 45 秒。
- 自己用命令行起的飞鱼引擎，界面以前显示「未启动」（因为只认本程序的子进程），却又显示首声指标 ——
  现在状态里区分 `running / owned / external`，「一键启动」也会真的把模型装进显存（实测 23 秒 → `ready=true device=cuda:0`）；
  「关闭引擎」对外部进程只卸载模型，不杀别人的进程。

## 用量：设置里新增一页，看得见她花了多少

- 第 8 页「用量」：今天 / 近 7 天 / 累计、按来源的占比（DSH 对话 / 自定义 API）、近 14 天柱状图、
  最近 24 轮明细（时间、来源、模型、输入、输出、合计）、账本文件位置与清空入口。
- 「上下文」卡：上一轮读进去多少、占上限几成（≥70% 转黄、≥90% 变红）、最近 12 轮走势。
  写明「上下文每轮重置，不等于累计消耗」，免得把两件事看成一件事。
- 输入+输出 ≠ 合计时，差额是缓存命中的上下文，现在标在输入列里（`6,120 +2.6k 缓存`）。
- 采集三处：DSH 侧 `turn_end` 的 usage（含「看屏幕」那条独立会话）、自定义 API 侧的响应体 usage；
  账本去重、120 天 / 600 轮自动裁、原子写盘。**只存在本机。**

## 游戏模式之后还能拖能点

窗口藏过再显示时，Windows 侧的鼠标命中区可能还停在「整窗穿透」，表现是 hover 有反应、按下去什么都不发生；
渲染层的 `pointerup` 也可能永远不来，`dragging` 一直挂着。现在显示之后重设穿透、清缓存、重新置顶，并通知渲染层复位拖拽状态。
